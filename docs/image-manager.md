# Image manager

Open **Steamwork → Image**, in the position previously occupied by Asset Log / Steam asset checklist. Image replaces that checklist with image browsing, Inbox review, options and directional synchronization. Configuration and saved Inbox review remain collapsed until needed; checking or importing pictures opens their review. A single available option does not repeat its thumbnail beside the main preview. The separate Document row and Promo Art-adjacent shortcut have been removed; the existing standalone URL remains compatible. Opening the panel reads the saved catalogue; scans and synchronization run when requested.

Choose an existing local image folder. The folder holds the library; its `inbox/` accepts new pictures. Dragging files onto the page stages their original bytes in an inbox batch. PNG, JPEG, WebP, GIF, BMP, TIFF and ICO are supported. An optional separate folder can be used for an additional device or mounted drive.

The Notion destination is the user's existing **Draft / Steam Plan** page. Version 1.1.39 supports a single managed native image area on that page. Opening it shows pictures first, with short name-plus-dimension captions and an option label when needed to distinguish alternatives. Synchronization records and older explanations remain collapsed; existing explanation text and notes outside the managed image area are preserved. Existing folder targets remain compatible, without a new database or a second navigation entry. Personal page IDs and URLs remain private configuration. Native page support is a product capability; the user's actual page layout and completed synchronization require their own acceptance evidence.

**Check images** creates a persistent review plan without replacing originals. Byte hashes detect identical files, decoded pixel hashes detect identical static pictures in different formats, and matching titles plus real image dimensions identify replacement candidates. Animated pictures use byte identity and title/dimensions. A title or dimension match is a candidate for review, not proof of identical content. Existing filenames stay intact when indexing. New imports use `Title - WIDTHxHEIGHT.ext`, derived from the decoded format and dimensions.

Choose **replace**, **keep existing**, or **save separately** for each candidate, then confirm once. Replacements retain the original bytes under `.image-manager/history/`. Cross-format replacements use the incoming picture's actual extension and archive the previous format. Files and folder identities are checked again at the write boundary; stale plans cannot overwrite later changes. Completed plans have durable receipts, and safe local restoration refuses to overwrite subsequent edits. The page can restore pending plans and selections after reload.

The library groups pictures by purpose/title, then offers every available size and option. Within the selected size, left and right arrows cycle through the actual pictures in the same card, with a position such as **1 / 3**. A single picture keeps its simple preview. Changing size retains an explicitly linked option where available; separate purposes such as the main game and Playtest stay separate. Inbox new pictures with the same purpose, source space and known dimensions share the same navigation; each keeps its own admission choice, and confirmation still covers the complete review plan. Replacement, duplicate and ambiguous candidates retain their existing comparison cards. Browsing arrows only changes the visible picture. Different content with the same purpose and size can be **kept as another option**; identical content is labelled a copy. **Option information** edits the purpose, option name and an explicitly chosen source picture without changing the original file or its name. A different size alone does not establish a derivative. Missing remote source pictures remain pending links until their exact content is available. The title `Togo` displays as **透明Logo** (transparent logo); `Logo` remains a separate purpose unless the user explicitly groups it.

Option annotations stay in the existing local catalogue, keyed by original-file SHA-256. In-place image updates keep the known purpose and option slot; separate imports can create new options. Notion synchronization retains a versioned, small catalogue attachment alongside native originals so purpose, options and derivative references can return without uploading the same image again. The selected source determines metadata updates; previous catalogue versions remain available. Images and catalogue attachments are verified separately.

After editing option information, changed fields enable **保存并同步 / Save and sync** and **仅保存 / Only save**. The dialog marks edits as unsaved until the metadata save succeeds. **Save and sync** first saves locally, then pushes from **Console** to the configured Notion and optional device locations; an earlier Notion-source selection cannot turn this action into a pull. **Only save** leaves the change saved locally and waiting to synchronize, with a later action to sync that saved change. No changed fields and no pending synchronization means no additional save or push. With no external destination configured, the result says that the change was saved locally.

The status distinguishes unsaved edits, a local save waiting to sync, synchronization in progress, verified completion and an incomplete or partial result. A save failure preserves the entered fields and starts no synchronization. A synchronization failure preserves the local save and its retry state; retrying a partial result targets only unfinished locations. Uncertain Notion delivery retains the original request ID and is checked without silently posting a new transfer. Root, page, device, original-file hash and saved annotation changes invalidate late results. A device plan must itself match the saved root, destination and outward direction before any new files can be applied. Same-byte device copies can receive annotation updates without rewriting their image bytes; other file differences still require the applicable review.

Pictures still in Inbox must first be confirmed for admission. Saving their option information reports that it is saved in Inbox and waiting for admission; it neither publishes that picture nor applies other pending Inbox candidates. A save-and-sync push does not scan or consume an earlier Inbox plan. Unsaved location fields must be saved before starting either the top-level synchronization or save-and-sync.

**Sync** uses a selected source and destination. A conflict-free batch of new images may be added by that click; replacements require the review choices. Reading errors remain visible. Device synchronization uses the same review and original-byte copying.

Notion synchronization starts a dedicated, short-lived, signed-in Codex app-server connection only when requested. It makes fixed Notion tool calls without starting a model turn, extracting credentials, or scheduling a monitor. Calls are scoped to the configured native page or compatible folder and its returned original-file references. Availability and a verified connection are shown separately.

Uploads append native Notion file attachments, retain previous remote versions, and are complete only after downloading the attached original and matching its size and SHA-256. Exact duplicates already present are skipped. Uncertain upload or attachment receipts are retained for review and are never silently retried. Downloads enter the local inbox review workflow. A sync record's completed transfer and a pending local replacement are distinct states. Previously attached originals and catalogue files with complete verification evidence can be rechecked only within the same request and scope; this reads and verifies the existing originals and catalogue without uploading or attaching them again.

Notion transfers currently accept at most 50 originals per batch and 20 MiB per original; originals are not resized. Local imports accept 64 MiB per original and 96 MiB total per batch. Configuration and private synchronization receipts live in the existing Console user-data directory; the local catalogue and plans live in the selected folder's `.image-manager/`. No personal folder paths or Notion page IDs belong in release defaults.

Validation: `python tools/check-image-manager.py`, `python tools/check-image-manager-http.py`, `python tools/check-image-manager-notion.py`, `node tools/check-image-manager-ui.mjs`, and the existing desktop management-entry and package checks. The UI fixtures cover save-only/reload, dirty and no-op handling, local-save failure, fixed Console authority, unfinished-target retries, unknown request identity, stale result scope and preservation of unconfirmed Inbox work. Integration checks use disposable libraries. Real original-file transfer, the requested page layout and the same request's actual completion receipt each require their own acceptance evidence; source or fixture success alone does not establish that the user's Notion page was synchronized.
