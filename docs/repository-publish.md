# Console 多仓库提交与推送

入口只在桌面 Console 标签页，位于栏目导航上方：`推送到 GitHub`、展开箭头和简短状态。
箭头只展开仓库，不执行推送。展开后是动态仓库列表，显示实际仓库名称、版本和状态，
每行有单库`配置`，上方有`配置全部`。仓库数量来自已保存配置，不固定为五个。
单库配置只打开所选仓库；路径、远端、同步映射和版本来源等细项按需展开。
配置默认关闭。命名、说明预览、执行详情与单库重试也按需显示。
设置自动保存；尚未保存或格式错误的配置不会触发上传。

仓库展开行会核对待提交文件、明确配置的已保存工作文件同步差异及本地待推送提交。
有实际差异时版本文字为绿色；已核对无变化时使用主文字色（暗色主题为白色）。
读取失败或来源不明会单独提示，不把未知状态显示成“无变化”。待推送与待提交分别显示。
本地远端跟踪引用仅用于提示，真正提交前仍重新核对远端，不自动拉取、合并或强推。

多插件仓库的常驻版本栏只显示短的 `上传 #N`。点击带下划线的序号，才展开各插件真实版本，
以横线分开“本次有改动”和“其他插件”；读取、上传和重试期间也不把整串插件版本塞回仓库行。
序号是本机 Console 核验成功的上传记录，不是插件的软件版本，也不是 Git 全部历史的提交数。
它按真实仓库和目标分支保存；同一提交重试不重复计数，无变化、失败和待核验不增加。
旧数据只沿用具有固定目标、原提交和远端确认记录的交付资料，不猜测 GitHub Desktop 的旧上传次数。
记录未知、损坏或写入未确认时显示 `上传 #?`；保留原提交与记录供核验，不默默重置为零。
各插件版本仍独立维护，完整明细保留在配置、提交预览和提交正文中，不改变命名、升版或提交范围。

执行期间紧凑状态显示“已处理 N/总数”、当前仓库和实际阶段（检查、同步、远端、版本、提交、上传、核验）。
每个仓库显示自己的阶段、耗时及真实 Git／LFS 传输进度；只有远端核验成功才显示完成。结束后分别统计成功、跳过、需处理和待核验，
全部处理过不等于全部上传成功；状态回执断线时保留已知进度并标记等待核对。
点击对应仓库的短状态可展开原执行详情和单库重试，关闭后恢复紧凑显示。

尚无上传回执时，版本读取、当前配置和未知状态也可以点击。单库弹窗显示已核对的
原因与下一步，初次打开停在弹窗顶部。后端明确指出对应设置时，用户点击“查看对应设置”
才展开并聚焦路径／远端、同步映射、该组件的版本来源或备用标题；读取回执不抢焦点或滚动位置。
打开和定位只查看，不修改配置、不替用户切分支，也不执行 Git 修复。
不明原因保留安全原文，不凭提示文字猜测权限、同步或活动问题；正常说明不标为失败。

读取同一配置时保留上次版本，并明确显示更新核对中或读取失败。单库“重新核对”只发送
本机只读 GET，最多等待 60 秒，超时结束读取提示并保留已知结果和原请求。
旧来源或旧目标的迟到数据不能填入新配置，历史回执仍单独显示，不能按新目标重试。
未保存草稿、同步原始文字和一次性计划不会因查看原因或定位设置而丢失。

## 日常使用

上传暂停时，每行直接显示原因，例如等待 Codex 工作结束、已有暂存选择或需要处理远端历史。
点状态可看到“上次上传尝试”和该仓库“当前 Codex 活动”；当前核对只读取本机，显示具体聊天及其
实际声明的编辑范围。活动已经解除只表示可以重试继续仓库检查，不表示 Git 或上传已经成功。
加载、超时或失败保留原原因，关闭／换库／配置改变会取消迟到结果；不会自动再次提交。

Codex 工作使用当前 turn 的精确仓库编辑范围。只读和等待云端检查不阻断其他仓库；真正的编辑
与未核实的活动仍受保护。旧任务的遗留活动只有核对原生 App 的真实终止回执及文件指纹后才解除，
不会修改原始聊天历史、删除锁、按年龄猜测结束或忽略正在进行的编辑。

1. 保存工作文件。
2. 进入 Console，点击一次 `推送到 GitHub`。
3. 各启用仓库串行处理。失败的仓库保留原工作和提交，其他仓库继续。

初次配置复用开发者源码绑定、Blender 仓库绑定和 Work 工作区。
核对真实 Git 根目录、读取与推送地址、实际当前分支。
未找到本地路径的仓库保留为未启用配置，填写路径后再启用。
仓库数量不固定；可以添加、停用仓库并修改其独立目标分支。
不会替用户切换分支。

## 提交说明

默认开启“有改动自动升下一版”。先同步已保存的工作文件，再按实际改动范围选择组件；
版本没有被手动升过时，准备下一补丁版本并在同一次新提交中写入必要版本文件。
Summary明确显示例如 `1.6.43 → 1.6.44`。已经手动升过的版本保留，不再自动加一次。
仅有本地提交待上传时只推送原提交，既不升版也不改变原说明；完全无变化则跳过。
配置可以关闭自动升版，改为使用当前权威版本或明确选择一次性计划。
同一版本可以重复提交。推送不自动建立 Tag 或发布 Release。

应用的配套版本按已配置的真实合同一起维护。例如 WorldConsole 的 manifest、package
与 lock 文件根版本属于同一应用，会在同一提交里保持一致；依赖包版本保持原值。
独立插件仍各自读取和更新自己的版本。版本文件冲突、隐藏或无法安全写入时暂缓该库。

也可以在配置中明确选择该组件的一次性下一补丁版本，例如 `1.5.42 → 1.5.43`。
明确计划优先于自动选择；选择只保存计划，实际版本文件等用户点击主按钮才修改。
有效升版计划或已经发生的版本修改，会在 Summary 中明确显示 `原版本 → 新版本`。
未开启自动升版且未选择计划时，继续使用当前版本，不把建议版本当成提交后的版本。
补丁位以99为上限：`1.6.98 → 1.6.99`，`1.6.99 → 1.7.0`；
两位都达到99时为 `1.99.99 → 2.0.0`。
多个独立插件分别选择自己的版本，没有统一的虚构仓库版本。
同一 Blender 插件若同时在 `bl_info` 与 `blender_manifest.toml` 声明一致版本，
两处作为同一个组件的关联文件一起核对和升版；原值不同或无法明确读取时先暂缓。
计划绑定原版本和文件校验；来源变化、不明确或无法安全写入时暂停并说明原因。
提交成功后重试只处理原提交，不再次升版；尚未提交的恢复使用已冻结的同一份升版计划。
无版本来源的模型仓库仍使用已保存的备用标题，不新建版本文件。

Random-Realm 的日常进度版本来自明确的版本提交记录，例如 `1.6.43`，
与 Unity 的打包字段 `bundleVersion: 0.1.0` 分开。提交版本来源只读取当前分支
最近64条 first-parent 本地提交，接受完整的三段版本或版本过渡标题，并记录实际提交来源。
该来源的自动升版或明确计划只安排本次新提交的标题，
不修改 Unity 打包字段或创建虚构版本文件。
没有文件变化时不创建空提交；已有本地提交只推送其原说明，明确计划保留供下一次实际修改。

第二个预设为改动插件／模块名称和对应当前版本。
多个独立组件各自读取实际版本；不能确定单一版本时，使用已保存的备用标题，
默认 `更新进度 {datetime}`。版本明细、可选副标题与备注放入正文。
文件摘要只描述实际新增、修改、删除的文件，不从二进制变化猜测功能修复。
本地规则独立可用；没有新增 AI 服务、模型或密钥配置。

## 工作文件同步

只有明确保存的同步映射参与操作，先同步再判断 Git 变化。
沿用 Blender `tools/build_sources.json` 的依赖文件顺序，最后将已保存的
`Builder6.blend` 同步到仓库 `Build.blend`。
来源缺失、读取／复制期间变化、目标被其他程序改写或清单损坏时，暂缓该仓库。
已经复制的工作文件保留在工作树，失败不会回滚用户文件。

提交使用正常 Git 暂存、提交与推送，保留 `.gitignore`、LFS、过滤器和 Git hooks。
通用流程不套用 Console 开发者更新的源码白名单。
私人记录、凭证和缓存仍排除，也可配置附加排除范围。

## 保护与恢复

操作前检查远端真实分支。远端领先、分叉或操作中变化时，暂缓而不自动合并、
强推、重置或隐藏工作文件。
未完成合并／变基、已有暂存选择、已知 Codex／Work 正在编辑、活动状态无法核实，
以及提交时文件、分支、配置或索引变化，都会保留原状态并给出简短原因。
已有暂存选择采用保守策略：无论全量或部分暂存，都留给原操作者处理。

桌面 Codex 活动按真实会话边界核对。只有创建和更新时间均可核验、早于可信本次
Windows 开机至少 300 秒、会话文件明确缺失且再次核对仍缺失的旧记录，才单独归入
历史未知记录；不把它们说成已完成，也不改写 SDK 数据。近期、正在活动、权限不明、
文件或元数据变化的记录仍会暂缓对应仓库，避免把正在编辑的内容混入提交。

没有文件变化但已有本地提交时，只推送原提交，不改其说明。
提交成功后推送失败，原提交与目的地写入持久记录；下一次主按钮或单库重试
先核验并继续该提交，不再创建一份。
超时或回执不明确时，只有实际远端包含原提交才报告成功；无法核验显示待核验。
修改配置不能把未完成提交悄悄发送到另一仓库或分支。

浏览器在发送前持久保存请求编号与范围，后台对重复编号幂等处理。
刷新和重启只恢复回执，不自动重新发送。
后台明确确认某请求不存在时，详情提供用户触发的 `继续原请求`，保留原编号和范围。
其他仓库成功结果不会因单库失败回滚。

## 验证与触发范围

关键流程通过临时本地 bare 仓库、实际 HTTP 权限边界和隔离 DOM 场景验证。
测试模式只能访问临时目录中的本地远端；不使用真实仓库上传测试。
真实批量同步、提交、推送仅由用户点击主按钮或明确的单库重试触发。
初次发现、打开配置和说明预览不执行工作文件同步或网络推送。

## 每库进度与快速打开

工具列保留简短处理状态；展开列表后，每个仓库各自显示阶段、耗时和细进度条。
Git 对象传输与 LFS 文件传输使用进程实际输出的数量／字节百分比，明确标注对应阶段
或文件，不把它当作整个仓库的完成比例。排队、检查、同步、提交和远端核验采用
不定进度显示；只有远端确认原提交已接收，仓库才显示 100%。失败、暂缓、跳过和
待核验分别说明，点击状态可查看原因及已有的定位、重试入口。

打开列表先返回配置、实际操作回执和身份匹配的上次版本快照，再按库刷新。
最多两个只读检查器，每库有独立时限；较慢的仓库不会阻挡已完成的其他行。
核对符号旁保留原值，刷新失败也保留已知信息并允许单库重查；首次没有旧快照时
先显示已配置组件名称。显示缓存绑定安装身份、数据目录、路径、远端、分支以及
影响检查的全部配置，不用于授权升版、提交或推送。后台回传也核对实际读取来源，
迟到的旧目标结果不会覆盖新配置。重启缓存只是上次记录，提交仍做实时校验。
刷新请求去重，普通轮询不新增检查；离开 Console 停止浏览器的读取计时器。

仓库名称下显示最近本地提交距今的时间：`30s`、`12m`、`3h`、`2d`。
时间来自当前分支 HEAD 的实际 committer 记录，悬停可看完整时间和 SHA；
它与成功推送的核验时间分开。旧快照会明确标记为上次记录，未知显示 `—`，
未来时间显示 `?`。秒级更新只计算显示，不触发新的 Git 扫描或 HTTP 请求；
收起、切走、隐藏和销毁时停止该计时器。

## 1.1.13：长轮聊天范围核对

长轮离开 4 MiB 尾部窗口后，保留已核对的本轮原始 typed anchor，以最多 16 MiB 增量流读核验全部新增事件、原文件及声明身份。遇到新用户内容、新轮次、替换／截短、不完整或不合法事件及超限，继续保护未知活动；不按年龄推断结束或绕过真实编辑。
